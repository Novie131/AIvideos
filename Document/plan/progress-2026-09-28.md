## 3. 才藝軌 — ⏸ 五關過三關

目標：使用者上傳一段舞蹈影片，產出「人形小橘跳那支舞」。

```
① 姿勢抽取        ✅ Apple Vision，偵測率 100%，9 秒影片跑 1.9 秒
② 控制素材        ✅ 舞蹈影片合格（單人、全身、佔畫面 57%、每格 17.6/18 關節）
③ 人形角色        ✅ 兩個比例版本，小橘特徵全保住
④ VACE 接 API     ❌ ← **卡在這，已停損**
⑤ 實際跳舞        ⬜
```

### ① `studio/posegen.py`（244 行）

影片 → OpenPose COCO-18 骨架線框序列 + 關節座標 JSON + 控制用 mp4。

**MediaPipe 在這台機器上是死路，兩條都走過**：
- `1.0.1` 的 Tasks API **必崩** —— `TensorsToDetectionsCalculator` 初始化 Metal 時 abort（`DrishtiMetalHelper`），設 `delegate=CPU` 也擋不住
- `0.10.x` 的舊 `solutions` API **根本沒包進 arm64 的 wheel**（`mediapipe.python` 不存在）

改用 **Apple Vision framework**：系統內建、零模型下載、原生就有 `neck` 關節。
跟用 macOS `say` 做 TTS 是同一個思路 —— 先用系統已經有的東西。

順帶移除 `opencv` 依賴，改用 ffmpeg pipe 解影格（ffmpeg 本來就是硬需求）。

### ③ 人形小橘

`characters/orange-cat/ref/anthro-lanky.png`（比例接近人體骨架）
`characters/orange-cat/ref/anthro-chibi.png`（最接近故事軌的圓臉小橘）

三輪才拿到可用的，踩到兩個提示詞陷阱（已記入 `character.json` 的 `_prompt_traps`）。

### ④ 為什麼卡住

**8 輪測試、約 1.5 小時生成時間，全部失敗。** 詳見 ADR-013。

症狀：骨架圖經由 `init_images` 送進去，**被當成 img2img 的起始畫面，不是控制訊號**。
決定性證據：輸出的背景是深灰色 —— 那是骨架圖純黑背景以 `1 - strength` 的比例滲出來的。

**結論：VACE 的控制輸入不走 `init_images`，而 HTTP API 沒有暴露那個通道。**

## 6. 這個專案最值得帶走的三個教訓

**① 卡住時先問「輸入的形狀對不對」，不是「參數要調多少」。**
兩次大突破都來自這個角度：動作幅度的解法不是調 `strength`，是把動作凍結進出圖階段；
VACE 從單張圖改成序列，行為立刻改變（雖然最後仍不足）。

**② 推論要標記成推論。** 這次至少錯了五次，每次都是實測才發現：

| 推論 | 實際 |
|---|---|
| I2V 要 50 分鐘 | 3.5 分鐘（錯 14 倍） |
| 16GB 記憶體會爆 | Draw Things 用 mmap，瓶頸是磁碟頻寬 |
| 取樣器該用 Euler A Trailing | Z-Image 要 UniPC Trailing |
| MediaPipe 是標準解 | macOS 上是死路 |
| 「手臂跟著骨架張開」＝姿勢驅動成功 | 只是圖層混合的殘影 |

`pipeline-plan.md` 的信心標記（`[已驗證]` / `[官方規格]` / `[推定]` / `[待驗]`）值得維持。

**③ Draw Things 的 API 沒有文件，但核心是開源的。**
`ScriptModels.swift` 就是 API 的完整結構定義，`config_data_model_generated.swift` 有所有 enum。
`gh api repos/drawthingsai/draw-things-community/contents/<path>` 直接讀，比猜快太多。
另外它**傾向於靜默修正而不是拒絕** —— 尺寸不是 32 倍數會默默改、`inputOverride` 比對不中會落回預設、
`say` 未安裝的語音會產出空音檔。**接受不等於生效，一定要驗證輸出。**
